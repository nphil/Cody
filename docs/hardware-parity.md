# PC tool parity: what Cody does from a tablet or browser

Goal (owner, 2026-10-02): from Cody in Chrome on an Android tablet (WebUSB /
Web Serial through the existing browser bridge) do what a Windows PC does with
`mtkclient`, `esptool`, and `dfu-util`. The safety is the person's one-time
trust of the device (asked once, in the chat), automatic backups where the
protocol can read them, hard refusals for the writes nobody should make, and
readback verification.

This is the honest ledger of that goal. Every row says what Cody does **today**.
Architecture and rules live in `AGENTS.md` ("Browser-hosted hardware").

## How to read it

| Status | Meaning |
|--------|---------|
| **Done** | Implemented in Cody and exercised by the named tests against a fake transport. |
| **Composed** | No single action; reachable by combining actions (the recipe is given). |
| **Refused today** | The code deliberately refuses it. The rule is a policy choice, not a browser limit, and is listed under "Gaps" as work, not as a limitation. |
| **Not implemented** | No code yet. The reason is stated. |
| **Browser limit** | Cannot be done from a web page, with the exact reason. |

**Evidence level for every "Done" row: fake transports and local loopback only.**
No row has been exercised on real hardware by this change; each is
**UNVERIFIED on hardware** until its item in `docs/hardware-checklist.md` has
dated evidence. "Tests" below are `node --test` files under `lib/devices/`.

Tool names: all hardware tools take the browser `device` id from `device_list`
and a `protocol`. Every control operation (anything but `device_detect`) needs
the person's trust of that device: the first one asks once in the chat, and no
tool argument can answer for them.

### Trust: one question per device, and a countdown before the command goes out

There is no per-command approval. The person decides once per device whether the
agent may control it:

| | |
|---|---|
| The question | the first agent control operation on a device the person has not trusted raises ONE card in the chat's input dock: *"Let the agent control <device>?"* with **Allow**, **Deny** and *Remember this device*. Operations the agent starts meanwhile wait behind it (state *Waiting for your answer*) and raise no second card. **Allow** runs them all, in the order asked. **Deny** fails them all with *"The user declined control of <device>; do not ask again until they reconnect it"*, and the agent is refused with no new question until the device is unplugged and connected again. |
| What it covers | every action but read-only detection, on that device, until it disconnects - or for good when *Remember this device* was ticked. The user's own terminal and Devices-panel buttons are never asked about. |
| Remembering | per account, on the server (`device-trust.json` in the accounts directory). The key is the USB vendor id plus the serial number - not the product id - so the same unit stays trusted as it changes between adb, fastboot and recovery. A device with no serial number has no key: the checkbox is hidden and the trust ends when the device is unplugged or the page reloads. |
| Forget | the device card shows a *Trusted* chip with **Forget**; Settings (Preferences, Trusted devices) lists every remembered device with Forget. Both only REMOVE trust, and cancel what the agent had running on the device. |
| Who can grant it | only the Allow button on the chat card. The server stores what an authenticated page sends; no tool, operation option, server frame or access token can grant trust. |
| A wait before sending | any start tool takes `options.sendDelaySeconds` (whole seconds, 1-300): the card reads *"Starting in N s"*, nothing is sent, **Cancel** stops it at any moment, and a device that leaves the USB bus cancels it with the reason shown. It is not an approval. It runs once, before the first command. |
| The moment of sending | re-checked once more: still the same USB identity (`vendor:product:serial`), still connected, not more than 10 s late (`COUNTDOWN_SLACK_MS`: a page that slept through the countdown sends nothing). If not, nothing is sent and the operation fails with *"Not sent: ..."*. |
| An unanswered question | **does not time out.** It waits until the person answers, the agent cancels, or the device leaves the USB bus. |

Kept from before: backups before writes, readback verification, UNVERIFIED /
POSSIBLY MODIFIED reporting, the hard refusals (eFuse burns, EDL boot0/boot1/rpmb,
overlaps), the browser's own USB picker, and the request-level
`options.protectedOverride` that a request must carry for ESP / DFU / STM32 /
STK500 writes into a protected region. Bootloader and partition-table targets
carry only a PROTECTED note in the operation log: nothing more is asked.

Deliberately **not** built: a per-operation approval of any kind, approving
*before the operation exists*, and any way for the agent to ask for trust on the
person's behalf.

Pop-ups are for news, not progress. Hardware `notice` frames exist only for a
long (15 s) or bulk (flash / dump / pull / push / sideload / install) operation
finishing, a failure, and a cancel the system made. Started / progress / output
events and a routine read that succeeded raise nothing; a burst of failures is one
pop-up plus one summary; a refusal the person caused by saying no raises none. In
the Devices panel the routine commands an agent ran (no risk declared, no file
saved) fold into one entry per burst - *"Agent ran 7 fastboot commands"* - whose
rows open to the full card of each command.

### The Devices panel: jobs, what needs you, history and the detail sheet

The panel tells what happened in the words a person would use, not one card per command. Pure model in
`lib/devices/jobs.ts` and `lib/devices/activity-groups.ts`; components in `components/devices/`.

- **A job is one task.** A flash or dump, or a run of the same bulk operation on one device (fifty-eight `dump`s,
  gap under two minutes, nothing different in between; routine reads do not break it) is ONE job that owns its
  operations. It has one state (waiting, starting soon, running, done, failed, stopped, cancelled, declined) and says
  how far it has got only as far as it can know: *n of N* needs the partition table the device reported (a backup only),
  an estimate needs a measured rate (the newest ten seconds of progress), and a total it cannot know is not shown.
  While a run is going its title carries no count (`Back up partitions`), because the count would disagree with
  *47 of 58*; once it ends the title says `Back up 58 partitions`.
- **Top to bottom by how much it needs the person:** *Needs you* (first, in reading order, never sticky: a pinned
  block of two cards would swallow a 360 px panel; a countdown that can still be cancelled, the one question waiting
  in the chat with how many commands queue behind it, a failed or system-stopped job, a failed zip or save) - at most
  two rows show, the rest fold; *Running now*; connect; the devices and their actions; *History* by device (only when
  several have any) and by day (today open, older days closed and counted); *Files & backups*. A failure stays at the
  top until the person presses *Got it* (`useAcknowledged`, kept per session in the page); a new failure in an
  acknowledged job raises it again. A stop the person made, and a refusal, are history, not alarms.
- **A command that merely looks routine** (an agent read with no risk declared) is not drawn while it runs unless it
  runs longer than two seconds (`ROUTINE_QUIET_MS`), so a dozen `getvar`s do not flash cards in and out of the top.
- **Nothing technical is written out in the feed.** Hashes, ids, logs and JSON live in ONE place, the detail sheet
  (`DetailSheet`): it covers the Devices panel only (the chat stays usable), the panel behind it is `inert`, Escape or
  the close button ends it and focus returns to what opened it. It is reached from a job, a command in a burst, or a
  file's menu. The panel's own scroll and the sheet's body are the only scrollers; no card contains one.
- **Files** follow the jobs: one card per set (`groupArtifactSets`), partition names as labels, a menu per file
  (Download, Copy SHA-256, Copy id, Use as input, Details, Remove; Remove asks first), a filter and sort past ten
  files and a first page of twelve with *Show all*. A set's ⋯ menu adds *Combine with the older backup* (it asks first)
  and its opened card has *Select files* (checkboxes, *All* / *None*, *Download selected*, *Save selected*). What the
  person added is its own short group.
- **Tests:** `lib/devices/jobs.test.mjs` and `activity-groups.test.mjs` (grouping, phases, progress and estimates,
  attention order, acknowledgement, day grouping), `components/DeviceActivity.test.mjs` and `DeviceFiles.test.mjs`
  (what each card says, the detail sheet, the menu keys, the three languages), `components/DevicePanelLayout.test.mjs`
  (a real browser at 320, 360 and 480 px: no sideways scroll, every control at least 44 px).

## Files & backups: sets, one zip per backup, "Download all", "Save to server"

Everything a device operation saves lives in the browser (IndexedDB, the "Files & backups" list), so keeping it
means moving it out. A backup of 58 partitions is 58 files; both ways out turn them into ONE compressed `.zip`,
whatever the device: a download is one file in the Downloads folder, a save to the server is one file in the vault.

| | |
|---|---|
| Sets | Every output records its provenance when it is saved: the operation, device, protocol, action, target and command, the device's name, **when the operation began working with the device (`startedAt`)**, the **`set` name** an agent gave it and, for a backup that declares it (the EDL `backup` command), **which partitions it took** (`scope`: the chosen ones and every one the device listed). `groupArtifactSets` (`lib/devices/artifact-sets.ts`, pure) turns the files into sets: (1) files filed under one name on one device (the agent's `set`, or the name a person's Combine gave them) are one set, whenever and with whatever command they were made; (2) otherwise one operation is one run, and consecutive runs of one kind on one device are one set when no more than two minutes pass between the END of one run (its last file) and the START of the next (when its operation began), so a read that takes ten minutes never splits a backup, while a different kind of run on that device in between ends the set; (3) a file saved before the start was recorded (everything 0.53 saved) has its start estimated as its save time minus its size at 1 MiB/s, floored at the end of the run before it on that device (a device does one thing at a time, so the estimate can bridge the quiet time to the run that really came before it and never places a run before runs it followed), which turns the six cards 0.53 showed for one tablet's 56 single dumps into two without anyone doing anything: the backup's 55 dumps, and the devinfo read three quiet minutes before the first of them (Combine joins them); (4) files with no provenance are grouped by file name and time and marked `legacy`. A set made of backup operations that declared their scope (and nothing else that could hold a partition: a table read beside them is fine, a dump or a restore's copies is not) is labelled **Full backup · N partitions** or **Backup · K of N partitions** (the union of what they declared) only when it holds every file those backups saved, which means the manifest each writes last and exactly its N+3 files; otherwise it is **Incomplete backup · N files**, and its zip is named `…-incomplete-…`: a backup that stopped part-way, or lost a file to Remove, never reads as a full one on a card, in a file name or in `manifest.json` (`backups[].kind` is `full`, `partial` or `incomplete`, with `files` and `complete`). An agent's save names its zip the same way, with `(N files)` when it keeps only some of a card's files. A named set shows its name. |
| Combine | A set's ⋯ menu offers *Combine with the older backup…* (the next older set of the same device; it asks first). The older backup must be a backup of the same device (for files 0.53 saved, the same Qualcomm unit tag in their names; files with neither have no older backup) and the same protocol, never a restore's safety copies or a table read; the question names it and its date, and the store refuses if the list changed and it is no longer that set's older backup. It files every file of both sets under one set name (the older set's, an agent's, or one made up that no card shows) in a small database of its own (`cody-device-artifact-sets`, one row per file), so a backup's Blobs are never rewritten for it, the combined set survives a reload, and a later operation under an agent's name still joins it. The filings live apart from the files' own database on purpose: Cody 0.53.0 reads every row of that database as a file, so a rollback keeps its list working and simply shows the sets grouped by time again until 0.54 runs. It is refused, and the menu item disabled, while a transfer is reading either set or a job is still making their files. |
| Choosing files | Opened, a set can turn its list into checkboxes (*Select files*): *All* / *None* act on the whole set (not only the rows on screen) and the count says how many of how many and how big. *Download selected* and *Save selected* make ONE archive of just those files (`downloadArtifacts` / `saveArtifactsToServer` take any list of ids). *Download all* and *Save to server* still take the whole set. |
| Choosing partitions | EDL `device_exec "backup"` takes `options.partitions` (exact GPT partition names from `printgpt`; omitted means every partition). The panel's backup-set card lists the partitions of the last partition-table read as checkboxes with *All* / *None*, a count, a filter and a first page for a long table, and starts a backup of just those (all ticked sends no `options`: the same full backup as before). A backup of chosen partitions is still ONE set and ONE archive. It reads only the chosen partitions and both partition tables, declares its scope to the operation (`declareScope`: `chosen` in disk order, `all` in table order) before it saves its first file, says "5 of 56 partitions" in its confirmation, log and result, and its EDL manifest is `restorable: false` ("This backup holds 5 of the 56 partitions on the disk. Cody restores only a whole set; put these partitions back one at a time with device_flash from their saved files."); `exec restore` refuses it with that explanation. Only the protocol that can list partitions offers this: no flow was invented for the others. |
| The archive | One ZIP per backup (`lib/devices/artifact-archive.ts`, the same writer in the browser and on the server). Under one folder named like the file: the device files in order, `SHA256SUMS`, `manifest.json`. Every device file is deflated (`CompressionStream("deflate-raw")`, default level) as it streams through, with flag bit 3 and its CRC-32 and sizes in a data descriptor after the data (16 bytes; 24, with 8-byte sizes, for a ZIP64 entry), so nothing is measured first. A file of 0 bytes and the two small metadata entries are stored (CRC and size in the local header, no descriptor), so any tool can read them without inflating. ZIP64 records are written where a classic field cannot hold the value: an entry of 4 GiB less 16 MiB or more (deflate cannot grow data by more than about 0.04 %, so a smaller entry always packs to a classic size), a header offset or the directory past 4 GiB, or 65,535 entries or more; anything smaller is a classic archive. The writer is pull-based (one slice of one file in memory; a consumer that stops pulling stops the reading) and never produces a plausible-looking bad archive: a file whose stream has another length than announced, or bytes that no longer match the CRC-32 recorded when it was saved, fails the whole write. `manifest.json` (`cody-device-artifacts/2`) lists every file (name, path inside, size, SHA-256, kind, source, the operation with its device, command, start time, set name and partitions), `compression`, and for backups that declared a scope `backups`: which partitions were chosen and every partition known at the time; `sha256sum -c SHA256SUMS` works after extracting. A partition dump is mostly empty space and shrinks to a fraction (64 MiB that is almost all zeros packed to about 65 KB); encrypted data does not shrink and grows by about 0.03 %. |
| Download all / selected | `deviceArtifacts.downloadSet` / `downloadArtifacts`: the archive above, streamed. Desktop Chrome/Edge: the Save-as picker opens first (it needs the click) and the archive streams into the chosen file; a failure or a cancel discards the half-written file. Without a picker (Android Chrome, Firefox, Safari) the compressed chunks are gathered into ONE Blob, folded every 64 MiB so the page's JavaScript memory stays flat, and handed to the browser's own download. The card says "Downloaded as X.zip · 3.8 GB → 610 MB". |
| Save to server / selected | `deviceArtifacts.saveSetToServer` / `saveArtifactsToServer`: the page uploads the raw files to the artifact vault (`lib/devices/artifact-vault.ts`). The save is announced with every file's size and SHA-256 (and a key made of them, so asking again finds the same save), written under `<root>/.incoming/<id>/`, appended in 4 MiB slices at exactly the offset the server holds (a retry cannot duplicate or skip a byte; a dropped connection or a reload carries on), and each finished file is **read back through the file system and hashed** before it counts (after an fsync: this catches a transfer or logic error and a torn write, not a media fault that appears later). Only then does the server pack the verified files with the shared writer into `.incoming/<id>/.archive.part`, **re-read the finished archive with an independent reader** (`artifact-archive-verify.ts`: the end records, every local header against its central record, every entry inflated through `node:zlib` while its CRC-32 and SHA-256 are taken and compared with the central record, the data descriptor and the SHA-256 recorded for that file, and the `SHA256SUMS` lines), move it in ONE rename to `<root>/<label>-<date>.zip`, and delete the raw files and the incoming folder. A reader of the root sees finished archives and nothing half-written, and the vault holds one file per save. Packing takes minutes for a big save, so it runs in the background: `complete` answers `complete` within about 20 s for a small save and otherwise `building` with how many bytes are packed, and the page polls until `complete` (so no request is long, and a reload or a restart loses nothing). The same files saved again answer `alreadySaved` and send nothing. The card says "Saved · 1 file · 3.8 GB → 610 MB". |
| Where | `<Cody data dir>/cody-device-artifacts` by default; `CODY_DEVICE_ARTIFACTS_DIR` moves it. A finished save is ONE file there, `<label>-<date>.zip` (the label as the card names it, cleaned; the date in the person's own time zone; `-2`, `-3` when the name is taken); its own `manifest.json` is how a save is recognised, listed and owned, and anything else in the folder is ignored. Unfinished uploads and the archive being written live under `.incoming/<id>/`, which is empty once saves finish. Directories are 0700 and files 0600 (a root the owner prepared keeps the permissions they gave it). `CODY_DEVICE_ARTIFACTS_MAX_GB` caps the whole folder (default 256, `0` for no cap): it counts finished archives at their real size and, for every unfinished save, its files plus a packing allowance (0.1 % plus 4 KiB per file and 4 KiB), so a save the cap admits can always finish; it is looked at again every 64 MiB of packing, so a cap lowered since the save began still stops the build cleanly. **Saves made by 0.53.0 are folders: they are left where they are, are no longer listed and are not counted against the cap, and an upload 0.53.0 left unfinished cannot be resumed.** |
| Bounds | 8 MiB per slice (the framework buffers only the first 10 MB of a request body once a proxy sits in front of a route and silently truncates the rest, so the server checks every slice arrived whole), 32 GiB per file, 64 GiB and 4,096 files per save, 1 GiB free on the disk at every step: when the save begins it needs room for its files, as much again for the zip that is written beside them before they are deleted, what other unfinished saves are still owed (only ones someone sent a slice to within the last hour: a save left behind keeps its folder until the retention period but not the room, and the refusal names the saves that do hold it), and the 1 GiB; every slice and every 64 MiB of packing look again (`disk_full` names the free space); and an unfinished upload nobody touched for 7 days, or a partial archive nobody wrote to for an hour, is deleted by the next save. A full disk or the cap while packing deletes the partial archive and keeps the uploaded files (`buildError` says why; saving again packs without sending anything twice). A finished save is never deleted for the person (`DELETE /api/devices/artifacts/saves/<id>` removes one). |
| Names | A name the browser chose is data, never a path: separators, drive letters, control characters, Windows-reserved names and leading/trailing dots are reduced to one safe segment (`lib/devices/artifact-names.ts`, shared by the zip and the server), unique ignoring case, and `manifest.json` / `SHA256SUMS` are moved aside. The archive's name is built by the server from the label and the date; ids are generated by the server and checked against a pattern before they touch a path. The vault's own files in a save's incoming folder (`.state.json`, `.<n>.part`, `.archive.part` and the temporary files it writes through) all start with a dot, which no cleaned name can, and `isVaultInternalName` reserves them a second time, so a file called `state.json` or `0.part` is saved as itself and can neither overwrite nor be overwritten by the vault's bookkeeping. A slice the disk takes only part of is written to the end; if the disk stops taking bytes the answer is a 507 `disk_full` carrying the length really stored, never a claim of success. |
| Who | The routes need the same credential every route does (session cookie, personal access token or Basic), and a save belongs to the account that made it and to a chat that account can open (`canAccessSession`): another account's save is reported as missing, not forbidden. An open instance (no accounts) sees everything. |
| Agents | Every start tool takes `set`, a name for the backup: the files of every operation with that name on that device are ONE set and ONE archive, whatever the timing or the command, so an agent that backs a device up step by step names every step the same (a name specific to this backup, because a later operation with the same name joins it). `device_artifacts_save` (`operationId` / `operationIds` / `fileIds` / `set` / `files` / `all`, `label`, `waitSeconds`) and `device_artifacts_status`: `set` selects every file filed under that name, `files` keeps only files whose name or partition matches (a name that matches nothing is an error that lists it). The tool asks the page, the page runs the same save the button runs (listed in the Devices panel as the agent's), and the answer is the archive: its path, its size and the original size, how many files are inside, that the server re-read it and every file matched, and `unzip -t '<archive>'` to check it yourself (inside, `SHA256SUMS` and `manifest.json`). While it is packing the status says so with a percentage, and a failed build is reported with what to do. The upload runs in the browser, so it continues only while the Cody tab is open; the status tool reads the server's own record, and only saves this chat's agent started. Like every working device tool they are offered while a device is granted. |

Routes (`app/api/devices/artifacts/saves`): `GET ?sessionId=` lists finished saves (archive path and size, name and SHA-256
of every file); `POST` announces a save; `GET|PUT|POST|DELETE /<id>` read its status (`uploading`, `building` with
`packedBytes`, or `complete` with `archive` and `archiveBytes`), append a slice (`?file=&offset=`), verify a file or complete the
save, and abandon or delete it. Errors are `{error, code}` with plain-English messages (`disk_full`, `quota_exceeded`,
`too_large`, `hash_mismatch`, `offset_mismatch`, `truncated`, `archive_check_failed`, ...); a build that fails after `complete` has answered
`building` shows as `uploading` with every file still verified and a `buildError`.

Evidence: `artifact-archive.test.mjs` (the classic, forced-ZIP64 and wide-entry archives are opened by `unzip -t`, Python's
`zipfile` and Cody's own reader; ZIP64 headers for 4 GiB+ entries, offsets and directories are checked on virtual sizes and on a
sparse 5 GiB entry; 65,535 entries; names, a changed or damaged source, cancel and backpressure), `artifact-download.test.mjs`
(the picker and Blob paths, progress, cancel), `artifact-archive-verify.test.mjs` (the independent re-read accepts archives
made by Python and by the writer and names 17 kinds of damage), `artifact-vault*.test.mjs` (slices, resume, damage, limits, names,
permissions, accounts, one file per save, a full disk or cap while packing, a delete during packing, a restarted server),
`artifact-transfer.test.mjs` (the real uploader against the real handlers with dropped connections, lost answers and damaged
bodies, and the polling through `building`), `artifact-tools.test.mjs` (an agent's save end to end), `artifact-sets.test.mjs`
(long reads, the owner's 56 dumps, names, combine, scope), `artifacts.test.mjs` (provenance, combine surviving a reload),
`components/DeviceFiles.test.mjs` and `EdlWorkflow.test.mjs` (what each card says in three languages). A real Chromium
(headless, with the panel over simulated hardware, a real dev server and the real vault) ran a 92 MB save and download
(a 64 MiB almost-empty file, an 8 MiB random one, a 16 MiB empty one): 8.5 MB archive each way, Combine surviving a reload from
the browser's own IndexedDB. **Not run on hardware, nor with the archive opened by Windows Explorer, macOS Archive Utility or
Android's Files app (only Info-ZIP `unzip` 6.00, Python `zipfile`, `zipdetails`, `zipinfo`, JSZip and Cody's own reader have
read it), nor in a real picker: the anchor download of a multi-gigabyte Blob on Android Chrome is the one path only a tablet
can prove.**

## adb

Cody speaks ADB to `adbd` directly over WebUSB (`@yume-chan/adb`); there is no
adb server, so `start-server`, `kill-server`, `mdns`, and `-s SERIAL` have no
meaning (the browser's device grant is the selection).

| PC command | Cody | Status | Evidence |
|------------|------|--------|----------|
| `adb devices`, `get-state`, `get-serialno`, `getprop` | `device_list`, `device_detect` (banner, model, product, Android release, shell protocol) | Done | `adb.test.mjs` (CNXN/AUTH/legacy-probe, run through `detect`); the `getprop` fields themselves have no test |
| `adb shell <cmd>` | `device_exec` protocol `adb`, once the device is trusted (the one question in the chat; there is no shell grant and no restricted tier) | Done | `adb-shell.test.mjs` (quoting, stderr/stdout, exit status, the trust gate and its end at disconnect) |
| `adb shell` (interactive), `exec-out` text | `device_monitor` / `device_monitor_send`; user terminal in the Devices panel (the person's own, never gated) | Done | `adb-shell.test.mjs` (terminal tests) |
| `adb logcat` | `device_exec "logcat ..."` (device trusted); runs until cancelled | Composed | none dedicated; streamed shell output is `adb-shell.test.mjs` |
| `adb push` | `device_push` (verified staging + atomic replace; raw/symlink direct push offers a backup and is declared for the exact path) | Done | `adb-transfer.test.mjs`, `adb.test.mjs` (resume) |
| `adb pull`, partition dumps (`dd` over shell) | `device_pull`, `device_dump` (stream to a session artifact with SHA-256) | Done | `adb-transfer.test.mjs` |
| `adb install` | `device_install`: the APK (a session artifact) is staged to `/data/local/tmp` with the push path's chunked, hash-verified, resumable copy, `pm install` runs on exactly that file, and the copy and staging files are removed when the copy fails, when `pm` fails, and when the user cancels. Cancel ends the wait for the package manager at once, even when it is silent or has not yet acknowledged the stream it was asked to open, without closing the connection: the removal runs over that same connection (also after the copy resumed on a replacement one), and the whole cleanup (waiting for the connection, opening the stream, running `rm`) is bounded to 10 s so the device is always given back. Cancel also ends the authentication of a replacement connection that is still waiting for the daemon (a copy resumed after the cable was pulled), and cleanup never starts a new authentication: with no authenticated connection left there is nothing to clean over, and the content-addressed staging names are reused or replaced by the next run. The result tells the operator the package manager may still finish installing. A cancelled operation never reconnects. Replacement is off unless `options.replace` is set: Cody passes `-R` on Android 9+ (where the package manager replaces by default and `-r` is ignored) and nothing on older Android (where `-R` is an unknown option and refusing replacement is already the default); an unreadable API level is treated as modern. The declared risk names the exact `pm install` command and the APK's hash (nothing is typed or asked; the device's trust covers it), and a file with no `AndroidManifest.xml` is refused | **Done** (implemented, host-tested; hardware evidence pending). The one step Cancel cannot interrupt is a sync write of a single chunk in flight (4 MiB at most) | `adb-admin.test.mjs`: "an app that is already installed is replaced only when replacement was requested, on the package manager's real rules" (emulated `pm` with Android 14, 9 and 8 rules), "an install started through the manager declares the exact package and command, then installs exactly those bytes", "an agent install waits for the one trust answer and touches the device only after it", "a copy that fails verification, runs out of space, or is cancelled leaves nothing behind" (real `/bin/sh` for the staging commands), "a cancel after the copy resumed on a replacement connection still removes the APK and its staging files, over that connection" (two distinct transport objects over one storage), "cancelling while pm install is running ..." (a package manager that has started and stays silent, over both the exec and the shell v2 protocol) and its manager-level twin (state `cancelled`, device released only after the cleanup), "cancelling while the replacement connection is still authenticating ..." (a daemon that never answers the CONNECT; flasher and manager level, both leases given back, no second authentication), "opening the package-manager stream or the cleanup stream is bounded by Cancel and by the cleanup limit ..." ### Forward / reverse: exactly what matches a PC and what cannot

Matches the PC: real byte streams in both directions over the device's own ADB
connection; many clients at once; `tcp:0` for a free port; the device-service
grammar (`tcp`, `localabstract`, `localreserved`, `localfilesystem`, `dev`,
`jdwp`); rules removed on cancel, device loss, page loss; reverse rule really
installed on `adbd` and really removed (`killforward`) before the connection
closes; no half-close (as on a PC, the first end closes the stream after the
bytes already sent).

Differs, with the reason:

- **"localhost" is the machine running Cody, not the tablet.** A browser cannot
  listen on a TCP port or dial a raw TCP socket, so the host end must be the
  Cody server. For an agent that is simply `localhost`. Apps on the tablet
  itself (Termux, other browser tabs) cannot reach a forwarded port, and a
  reverse cannot reach a server running only on the tablet.
- **Host side is always loopback `tcp:PORT`.** `adb forward tcp:... ` never binds
  a LAN address, privileged ports (< 1024) are refused, and Cody's own port is
  never reachable through a reverse. Host `localabstract:` / `localfilesystem:`
  endpoints are not offered.
- **Each rule is a long-running operation, declared before it starts,** not a
  fire-and-forget command. It keeps the browser tab and the USB connection in
  use; a locked screen or closed tab ends it.
- `--no-rebind` is the only behaviour: a host port already in use fails.

## Qualcomm EDL (the `edl` tool: Sahara + Firehose)
